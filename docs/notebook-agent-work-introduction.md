# Notebook Agent｜让收藏的视频真正成为可复用的知识

## 一、作品名称与介绍

**作品名称：Notebook Agent**

Notebook Agent 是一个面向视频知识管理场景的私人 AI Agent。它可以将用户保存的 YouTube、Bilibili 视频，以及通过浏览器伴侣获取的课程视频字幕，整理为私有、可检索的资料库。用户不必重新翻找收藏夹或拖动进度条，只需用自然语言提问，就能获得基于原视频字幕的回答、引用片段和可跳转的时间点。

它解决的不是“再建一个视频收藏夹”，而是让已经看过、收藏过的内容能够被重新找到、核对和使用。

## 二、需求起点人物与问题来源

项目的需求起点来自一位**匿名的项目发起者**对视频学习和内容收藏行为的长期观察。由于现有项目资料没有公开其姓名及可发布的个人背景，本文不补充未经确认的人物信息。

这项观察指向一个普遍而具体的问题：人们会不断收藏课程、访谈、演讲和行业分析视频，但真正需要使用其中某个观点时，往往只记得模糊印象，不记得视频名称、出处或具体时间点。传统收藏夹只能证明“保存过”，不能帮助用户回答“内容讲了什么”“依据在哪里”以及“如何快速回到原文”。

Notebook Agent 因此从“保存链接”继续向前一步，把视频内容转化为能够检索、提问和追溯的个人知识。

## 三、目标用户及其真实需要

Notebook Agent 主要面向以下用户：

- **深度学习者与学生：**经常观看长课程、公开课和教学视频，需要在复习或完成作业时快速找回某个概念及其上下文。
- **研究、产品与知识工作者：**会收集大量访谈、行业分享和案例分析，需要跨视频比较观点，并保留可核验的出处。
- **内容创作者：**需要从已看过的素材中重新定位论点、案例和表达，而不是再次逐条观看完整视频。
- **重视隐私的个人用户与自托管用户：**希望资料彼此隔离，并通过自己熟悉的 Web、MCP 或聊天入口访问私人知识库。

这些用户真正需要的不是更多收藏，而是：

1. 保存内容后由系统自动整理，减少手工摘录成本；
2. 通过自然语言找回观点，不依赖准确记住标题和关键词；
3. 知道回答来自哪段原文，并能直接跳回视频对应位置；
4. 在常用入口中随时提问，同时保证不同用户的数据相互隔离。

## 四、具体使用场景

### 场景一：复习长课程中的知识点

学生曾看过一段一小时的课程，只记得老师解释过某个概念，却忘记出现在哪一节。用户可以直接询问 Notebook Agent，查看相关字幕依据，并通过时间戳回到原视频继续学习。

### 场景二：比较多段访谈中的观点

产品经理或研究者保存多场人物访谈后，可以询问“这些受访者对用户研究有哪些共同建议”。Agent 会在个人资料库中检索相关片段，帮助用户比较内容，同时保留每个观点的来源。

### 场景三：保存需要登录的课程视频

对于 NTULearn/Kaltura 等需要用户登录后才能访问的课程页面，服务器无法直接读取内容。用户可通过浏览器伴侣，在自己已经授权的浏览器会话中提交当前页面的字幕和公开元数据，再由 Notebook Agent 统一整理。

### 场景四：在熟悉的入口中随时提问

用户可以通过 Web 应用或 MCP 使用核心能力，也可以选择接入 Telegram、微信等聊天入口。不同入口共享同一份私人资料库，使知识检索融入原有工作习惯。

## 五、Agent 的核心能力

Notebook Agent 的核心能力包括：

1. **多入口内容保存：**接收明确的 YouTube、Bilibili 普通视频链接，也支持浏览器伴侣提交当前 YouTube 或 NTULearn/Kaltura 页面的字幕。
2. **自动解析与整理：**在后台获取视频元数据和字幕，保存原始内容，按照语义切分文本并建立全文与向量索引。
3. **自然语言检索：**结合关键词检索与语义检索，在用户自己的资料库中寻找最相关的原文片段。
4. **基于证据回答：**回答只使用本轮实际检索到的资料，不用模型记忆补写资料库中不存在的事实；没有足够依据时明确说明未找到。
5. **来源定位与核验：**返回来源标题、原文片段和视频时间戳，用户可以直接跳回原视频核对上下文。
6. **资料管理与隐私隔离：**支持查看、搜索、备注、归档、恢复和失败重试；数据按用户空间隔离，Agent 不能自行选择或访问其他用户的资料。

## 六、使用流程

Notebook Agent 的典型使用流程如下：

1. **保存：**用户提交视频链接，或通过浏览器伴侣提交当前课程页面的字幕。
2. **整理：**系统异步获取元数据和字幕，保存原始材料并切分为可检索的内容片段。
3. **建立索引：**系统为内容建立全文索引和语义向量索引。
4. **提问：**用户在 Web、MCP 或可选聊天入口中用自然语言提出问题。
5. **检索：**Agent 只在当前用户的资料库中查找相关视频和字幕片段。
6. **回答与核验：**Agent 根据检索证据组织答案，并附上来源及时间点，用户可返回原视频确认。

整个流程形成“保存—整理—提问—核验—复用”的闭环，使视频从一次性观看内容转化为可持续使用的个人知识。

## 七、目标用户的实际体验反馈

项目曾通过一次真实的 Web 资料库预览持续收集目标用户的操作反馈。以下内容是对实际问题的匿名化归纳，不是虚构的宣传引语，也不代表大规模用户调查：

- 初始 URL 输入区域占用空间过大，输入少量内容时显得笨重；一次添加多个链接时，也不方便确认和删除其中某一项。
- 用户在搜索框输入关键词后，希望立即看到与现有视频标题、作者和备注相匹配的候选结果。
- 已经可以阅读的视频与仍在处理或处理失败的视频混在一起，用户难以判断哪些内容已经可用。
- 页面显示的视频总数包含了处理队列中的项目，但数字位于可阅读资料区域上方，造成数量与眼前卡片不一致的感觉。
- 较长的视频标题会压过封面，影响信息层级和阅读节奏。
- “为什么保存”更像解释性提问，用户希望改成更直接、轻量的“备注”。

这些反馈说明，用户不仅关心 Agent 最终能否回答问题，也会直接感受到内容保存、整理状态和资料找回过程是否清楚、可控。

## 八、根据反馈完成的优化与验证

| 用户反馈 | 完成的优化 | 验证方式与结果 |
| --- | --- | --- |
| URL 输入区域过大，多个链接不易管理 | 改为随内容增长的紧凑输入框；已确认链接显示为可换行、可单独移除的标签，并保留最多 10 条的数量提示 | 组件测试覆盖链接添加、移除与数量限制；桌面和约 390 × 844 移动视口检查均未出现横向溢出 |
| 希望输入关键词时立即匹配标题和作者 | 基于浏览器中已加载的资料生成本地搜索建议，可匹配标题、作者、收藏分类和备注；只有选择建议或正式提交查询时才请求服务器 | 回归测试覆盖建议展示、选择、失焦和外部点击关闭；桌面与移动端浏览器检查通过 |
| 可阅读内容与处理中内容混在一起 | 将已完成内容放入上方“可阅读视频”区域，将等待、处理、需操作和失败项目归入下方“整理队列” | UI 测试验证分区、状态和自动轮询；桌面及移动视口检查确认顺序、间距和进度显示正常 |
| 总数与当前区域卡片数量不一致 | 分别显示可阅读区域和整理队列的数量，筛选后同步更新当前区域计数 | 固定数据回归测试与筛选操作检查通过 |
| 长标题压过封面 | 保留完整标题，同时根据视觉长度切换更紧凑的响应式字号，并重新平衡桌面端封面与文字比例 | 长标题组件测试通过；桌面和移动端均验证标题完整且页面无横向溢出 |
| “为什么保存”不够简洁 | 将界面标签改为“备注”，保持底层字段与已保存数据兼容 | 聚焦组件测试及完整前端检查通过 |

上述优化完成后，相关版本通过了组件回归测试、类型检查、代码规范检查、接口契约检查和生产构建；项目记录中的对应前端验收为 **13 个测试文件、56 个测试用例通过**。同时进行了桌面与约 390 × 844 移动视口的浏览器走查。

需要说明的是：这些测试和浏览器检查证明功能按照反馈完成并可稳定运行，但它们不等同于新的用户好评或满意度数据。项目没有将自动化测试包装成用户评价。

## 九、当前能力边界与总结

Notebook Agent 当前完整支持服务器端导入普通 YouTube 和 Bilibili 视频；Bilibili 字幕仅限服务器无需长期保存账号 Cookie 即可访问的内容。浏览器伴侣目前面向 YouTube 与 NTULearn/Kaltura 等已经实现适配的页面，并不代表支持任意网站。Telegram、微信和浏览器伴侣属于可选入口，语音识别转写也尚未作为通用能力提供。

Notebook Agent 的价值不在于生成一段看似合理的答案，而在于建立一条可以验证的知识路径：用户先保存可信来源，Agent 再从私人资料库中检索并回答，最后把用户带回原视频的具体位置。它让分散的视频收藏从“以后可能会看”变成“需要时能够找到、确认并再次使用”的个人知识。

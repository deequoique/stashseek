# Agent 稳定性与有效性 Benchmark

> **2026-10-07 二次修订**：目标从"新旧版本对比 + 发布门禁"改为"对当前线上 Agent 跑一次 benchmark"。之前的方案存档在 `research/archived-release-gate-plan-2026-10-07/`。现状核查见 `research/meeting-gold-reuse-2026-10-07.md`。

## Goal

用已建成的会议 golden set，对**当前线上版本**的 Agent 跑一次可复现的 benchmark。每个数字都带分子和分母，用来回答三个问题：

1. **有效吗？** 能不能答出来、找到的证据对不对、引用准不准。
2. **轨迹符合预期吗？** 查资料的每一步是否按设计的规矩走。规矩见 R3。
3. **稳定吗？** 同一个问题多跑几次结果是否一致；工具出错时能否正确恢复；延迟和 token 用量是否可控。

题集、规则和脚本都固定下来。以后改了代码，可以重跑同一套，看数字有没有变差。但本任务**不做版本对比，也不设发布门禁**。

## Background

- **题库**：`data/meeting_gold/final`（dataset_hash `4aeccba…`）。
  - 来源：QMSum 的问题和参考答案，加上 ExplainMeetSum 标注的证据句。
  - val 集有 272 题、35 场会议，分三个领域，题型分 `specific`（具体问题）和 `general`（概括性问题）。
  - 题库里没有"答案不存在"的题，也没有时间戳。
- **跑题脚本已经有了**：`evals/meeting_gold`。它能把会议真实入库、调用真实的 `agent.stream()`、记录每次后端检索、计算证据命中。不过代码还没提交，只在本地 dev 上。
- **线上版本**是 `main`（PR #25，`7418262`）。dev 上有未提交的改动，跟线上不一样。所以 benchmark 必须在 main 的代码上跑，评测代码也要放到基于 main 的分支上。
- **已有参考数字**：同样 30 道 specific 题，每场会议一个账号，非正式运行。
  - 30/30 答出
  - 检索结果含正确证据 0.964
  - 引用含正确证据 0.893
  - 中位延迟 9.15 s，最大 17.5 s
  - 3 题出现被预算拦下的调用
  - 没有完全重复的查询
- **Agent 的工具**：
  - 会议问答应该只用文本检索类：`search_segments`、`get_neighbors`、`open_at`、`get_item`，外加内部的 `todo_write`。
  - 保存、删除、管理类工具不应出现。
  - 检索预算：共 5 次（搜索 2 次、扩展 3 次）。另有每次回答的请求数、工具调用数和输出 token 上限。
- **现在已经能记录的轨迹**：每次工具调用的开始/成功/失败/被跳过、实际执行的后端检索、查资料阶段的 token。
- **还记录不到的**：
  - 被参数校验拒绝的工具请求
  - 模型一次发出多个工具请求时的完整顺序
  - 写答案阶段的 token

## Requirements

### R1. 题集

| 题型 | 来源 | 数量 | 用途 |
| --- | --- | --- | --- |
| 具体问题 | 已有的 specific-30（其中 28 题有完整证据标注） | 30 | 有效性主体，可以和历史数字对照 |
| 概括问题 | val 中有完整证据标注的 `general` 题，三个领域都要有 | 10 | 看需要多处证据时，Agent 会不会绕圈 |
| 故障问题 | 从具体问题里挑，人为让检索工具失败一次（固定在第几次调用失败） | 8 | 看出错时能否按规矩恢复 |

- 每题跑 3 次，共 144 次运行。
- 题集写成固定文件，记录题库 hash 和题目 ID。故障方案也写在这个文件里，不修改题库本身。
- 只用 val 集。test 集留着以后做独立验证。

### R2. 运行环境和被测版本

- 只在 Neon 测试分支上跑，不碰生产库。复用 `prepare_test_environment` 的保护。
- 每场会议一个独立账号，和历史运行一致。
- 被测代码是 main 上的线上版本。报告里写明 commit、模型（`deepseek-v4-flash`）、thinking 设置和各项预算。
- 所有记录手段都挂在评测进程里，**不改 app 代码**，保证测的就是线上代码。

### R3. 预期轨迹规则

每次运行逐条判定通过或不通过。规则文件带版本号，跑之前定好，不在看到结果之后再改。

| 编号 | 规则 | 适用题型 |
| --- | --- | --- |
| T1 先查后答 | 回答之前，至少有一次成功执行的 `search_segments` | 全部 |
| T2 只用该用的工具 | 只出现文本检索类工具；保存、删除、管理类工具出现即不通过 | 全部 |
| T3 扩展有依据 | `get_neighbors`/`open_at`/`get_item` 操作的片段或条目，必须是本轮检索已经返回过的 | 全部 |
| T4 不重复查 | 同一工具加同样参数不出现第二次。例外：前一次失败后，允许的那一次重试 | 全部 |
| T5 不空转 | 不出现连续 2 次查询或扩展都没有带来任何新片段 | 全部 |
| T6 不撞预算 | 没有被预算拦下的调用，没有触发请求数、工具调用数或输出 token 上限 | 全部 |
| T7 引用可追溯 | 每条引用的片段都出现在本轮检索结果里，属于该题的会议，文本与库中一致；回答里的 `[S…]` 标记和引用列表一一对应 | 有答案的题 |
| T8 出错按规矩处理 | 工具失败后最多重试一次；之后要么恢复并正常回答，要么如实说明失败；不假装成功 | 故障题 |

另外报告"工具参数出错率"：被参数校验拒绝的工具请求占全部工具请求的比例。

### R4. 有效性指标

- **回答成功率**：正常返回答案、没有报错的运行占比。
- **检索命中率**：检索结果里含正确证据的运行占比。
- **检索覆盖率**：正确证据句被检索到的比例。分宽松口径（片段和证据句有重叠就算）和严格口径（证据句完整落在片段内才算）。
- **引用命中率**：最终引用里含正确证据的运行占比。
- **引用精确率**：引用的片段中，含正确证据的比例。
- **故障恢复率**：故障题里最终正常回答，或如实报错的比例。
- **答案正确率**：用固定的 LLM 对照 QMSum 参考答案打分，并人工抽查一部分，确认打分靠谱。

### R5. 稳定性指标

- **同题一致率**：同一题跑 3 次，"是否答出"结果一致的题目占比；"轨迹规则是否全过"结果一致的题目占比。
- **出错率**：报错、超时、超限的运行占比。
- **延迟**：每次运行从提问到最终答案的 p50、p95 和最大值。
- **用量**：每次运行的模型请求数、工具调用数，以及查资料和写答案两个阶段各自的输入/输出 token。

### R6. 报告和数据边界

- 输出一份 Markdown 报告和一份 JSON。
  - 按题型、按规则、按指标分别列出。
  - 每个数字带分子和分母。
  - 比例附 95% 置信区间（复用 `meeting_gold.stats.wilson_ci`）。
  - 和历史参考数字放在一起对照，并注明历史数字不是这套 benchmark 跑出来的。
- 某个数字没法算时（比如记录缺失），写"未知"并说明原因，不能当 0 或当通过。
- 每次运行的原始记录存在本地 `data/`（不入库）。报告里不放模型回答原文、工具参数或账号 ID。
- 再分发题库内容时，保留它的 NOTICE 和 LICENSE。

## Acceptance Criteria

- [ ] **AC1 题集**：题集文件通过校验。具体 30、概括 10、故障 8；三个领域都覆盖；文件里固定了题库 hash。
- [ ] **AC2 被测版本**：benchmark 在基于 main 的干净代码上运行，报告写明 commit 和模型配置。app 代码没有为评测而修改。
- [ ] **AC3 轨迹记录**：每次运行都能还原出完整的工具请求顺序，包括被参数校验拒绝的请求，以及同一次响应里的多个请求；写答案阶段的 token 也被记录。
- [ ] **AC4 规则检查器**：T1–T8 每条规则都有用假轨迹写的测试，正反例都覆盖，例如合法重试不算重复、有新片段的改写查询不算空转。用 specific-30 已有的历史记录回放，结果和人工核对一致。
- [ ] **AC5 指标**：有效性和稳定性的每个指标都有测试，固定分子和分母。缺记录时显示"未知"。
- [ ] **AC6 故障注入**：故障在指定的第几次调用准确触发，跑完后数据库里没有残留，不影响其他题。
- [ ] **AC7 安全**：只连测试分支。单元测试不连数据库。报告和日志里没有回答原文、工具参数、账号 ID 或密钥。
- [ ] **AC8 实际运行**：在测试分支上完整跑完一遍（144 次），生成报告，并人工抽查若干条原始记录，确认报告数字与原始记录一致。
- [ ] **AC9 不破坏现有功能**：`evals.meeting_gold` 的已有命令和测试，以及 `evals.natural_language` 的已有测试，全部照常通过。

## Out of Scope

- 新旧版本对比、发布门禁、LangSmith 上传。方案已存档，需要时另开任务。
- 根据结果修改 Agent。发现的问题另建任务。已知的检索排序问题（全库检索时多样性处理有害、关键词 AND 零命中）也不在这里修。
- 修改题库本身、视频题、35 场会议共用一个账号的场景、压力测试。

## 已确认（2026-10-07）

- **Q1 答案正确性打分**：做。用固定的 LLM 对照 QMSum 参考答案打分，再人工抽查约 10 题，验证打分是否可信。
- **Q2 题量**：48 题（具体 30、概括 10、故障 8），每题跑 3 次，共 144 次运行。
- **Q3 故障题**：放进第一版。
- **无答案题**：不做（用户 2026-10-07 决定）。benchmark 只用 golden set 里现成的问答对，不自己构造负例。"不瞎编"由答案打分（检查回答中是否有参考答案不支持的内容）和 T7（引用必须来自真实检索结果）覆盖；"库里完全没有答案时如实说没有"这个场景不单独测。
- **开发方式**：评测代码在基于 `origin/main` 的独立 worktree 里开发和运行，不在 dev 上写。原因是 dev 上有约 1000 行未上线的 Agent 改动，记录挂钩必须对准线上代码。提交前先征得用户同意。
